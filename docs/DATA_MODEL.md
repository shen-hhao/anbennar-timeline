# 数据库、来源与网页怎样一起维护

推荐一个 public 仓库作为协作入口，Pages 发布其 `dist/`。不需要运行在线 SQLite 服务，也不需要额外数据库服务器。

## 现有实况

维护者当前用 SQLite 管理研究记录，再导出网页读取的 JSON。SQLite 与 `dist/` 都包含来源、研究解释和本地追溯字段；不能未经公开清理就上传。直接复制数据库给贡献者，也不等于他能运行全部历史构建程序。

## 建议的正式数据布局（待实现）

```text
data/records/        按稳定ID或主体拆分的可比较文本记录
data/sources/        来源URL、作者、版本、短引文/摘要、定位和许可
data/decisions/      冲突、阶段方案、允许范围、采用与替代链
changes/            尚未采用的人工/agent提案
dist/               审核后生成、供静态网站加载的数据和程序
docs/               贡献、方法、公开版本说明
scripts/            经文档化的构建和检查工具
```

这是目标设计，不表示 JSON→SQLite→全部网页的单命令重建已实现。迁移时应先固定完整现状，再按现有表结构导出可审查文本，证明重建后的记录、关联、笔记和政治结果一致；不要用一次普通 SQL dump 冒充已经设计好的公开数据源。

共同维护时让文本数据和采用裁决成为主要审查面。SQLite 作为可再生成的查询快照，必要时在 GitHub Release 提供经清理版本及SHA。避免每次提交都携带几十MB的二进制差异。过渡期继续由维护者按已有精确采用流程处理提案，再导出站点；未完成迁移时明确标示这一限制。

## 来源与缺失

公开来源目录至少保留 source ID、可访问URL、版本/提交/修订ID、作者、访问日期、页码/行号/消息定位、实际阅读范围和来源族。哈希用于核同一原件，不能代替转载许可。

未公开附件仅保留允许公开的引用及缺失理由。不能为了让别人复现而上传私人聊天、个人资料、未获授权的整份文稿或整个本机模组。另一个贡献者可以提供可公开替代来源，也可在自己的合法本地副本上复核后提交结果。

数据库中的现有 manual 记录、国家关联、旧解释、被替代方案和不确定性不能在迁移中丢失。公开脱敏导出须有字段映射和语义差异报告；私人原始值继续由维护者保存，公开版不能靠静默删除导致来源结论失去依据。
